# Tenstorrent Blackhole P150 (experimental)

Strata can serve the **Coder IQ1_M** on a **Tenstorrent Blackhole P150** card. Strata's server (`serve/server.py`)
answers the requests as usual; the engine behind it is a separate implementation for the P150 written with ttnn and
custom Tensix kernels, in `tt/` (Python package `fnx`, its kernels, tests and tools). It runs in Docker, in the public
tt-metal image `lottolabs/qwen36-35b-tt-p150` (pinned by digest), and speaks Strata's engine protocol, so the OpenAI
and Anthropic APIs, the web chat, conversation reuse, streaming and cancellation work as with the CUDA engine.

**Experimental means:** one machine has run it (below). The NVIDIA, AMD and Intel engines are unchanged; nothing in
the CUDA build or in `serve/server.py` changes for it.

The engine's design, module contracts and measurements are in [tt/CONTRACT.md](../tt/CONTRACT.md).

## What runs on the card

- Every dense part of the model (hyper-connections, Gated DeltaNet, sparse QSA attention, per-layer embeddings, the LM
  head) on the P150, decode steps captured as device traces, MTP speculative decoding (3 drafts per step) with output
  identical to plain decoding.
- The routed experts are re-quantized for the card: GPTQ block-float 4-bit (BFP4) rows made from the published GGUF
  (see *Quality*). 8,680 of the 12,288 experts (85.9% of the routings) sit in the card's 32 GB; the others stay in
  pinned host memory and the kernels read them over PCIe inside the trace.
- `FNX_MOE=cpu` in the config's `env` runs the routed experts on the CPU with Strata's own kernels instead (exact
  Strata numerics, slower).

## What has been run, and by whom

| | Hardware | Result |
|---|---|---|
| Port author, 2026-10-08 | P150a (PCIe Gen4 x16 slot), 89 GB RAM, Linux, shared with another team's jobs | Coder IQ1_M, 32K context: decode 46.9 (chat) / 50.9 (code) / 50.0 (prose) tok/s with MTP, 30.9 / 29.2 / 26.6 without; `./setup.sh --backend tt` install, start, HTTP request and stop |

Numbers: `tt/fnx/tests/test_trace.py bench` (traced decode, greedy, the golden chat/code/doc prompts). About 8 ms of
the 37.5 ms one-token step is the PCIe read of the host-resident experts: the card supports PCIe Gen5, this machine's
slot runs Gen4, and a Gen5 slot should roughly halve that part [estimate, not measured].

## IQ3_S (development, not in setup yet)

The full Qwen3.8-Flash-Next (512 experts per layer) at IQ3_S also runs on the card, from a development checkout
(`tt/CONTRACT.md`, *Model variants*; `FNX_MODEL=iq3s`, picked automatically from the `--native` file name). By
default its routed experts run on the CPU with Strata's kernels, with the 4,671 hottest of them on the card as 8-bit
block floats; `FNX_MOE=device` moves every expert to the card instead (4-bit block floats quantized without
calibration data, 65% of them read from pinned host memory over PCIe).

| IQ3_S, 2026-10-10 | perplexity change | top-1 | mean KL | GSM8K-50 | decode, MTP (chat / code / prose) |
|---|---:|---:|---:|---:|---:|
| default (CPU experts + 4,671 on the card) | +0.63% | 0.974 | 0.007 | 46 / 50 | 33.8 / 29.7 / 33.5 tok/s |
| `FNX_MOE=device` | -1.55% | 0.916 | 0.061 | 46 / 50 | 28.0 / 28.8 / 33.5 tok/s |
| all experts on the CPU (the reference) | | | | 47 / 50 | |

Quality is measured against the all-CPU configuration of the same file (no float32 reference without a CUDA GPU).
Speeds: `test_trace.py bench` on the golden prompts; on general chat through the server, about 20-22 tok/s (default)
and 25-28 tok/s (`FNX_MOE=device`). `FNX_MOE=device` pins about 51 GB of host RAM; the default about 1 GB, but it
reads the experts from the GGUF in the page cache (about 55 GB of RAM to stay warm).

## What you need

| | |
|---|---|
| **Card** | One Tenstorrent Blackhole P150 (card 0), the tt-kmd driver (`/dev/tenstorrent/0`), `tt-smi` for board resets. |
| **System** | Linux. Docker, usable by your user, with access to `/dev/tenstorrent`. Hugepages help (1 GiB or 2 MiB pages); without them the engine pins 4 KiB pages, which works. |
| **RAM** | About 14 GB stays pinned while the model is loaded (host-resident experts). The tested machine has 89 GB. |
| **Disk** | About 160 GB: the GGUF shards (58 GB), the P150 expert set (35 GB), caches the first start builds (about 40 GB), the engine image (22 GB), pack and MTP files. |

## Setup and running

```
./setup.sh --backend tt
```

Setup finds the card, checks Docker, the image (pulled if missing), hugepages and the device lock, and offers only
the Coder IQ1_M with up to 32,768 tokens of context. It then does what it does for every engine: downloads the model
(or reuses one with `--gguf-dir`), writes the pack and the MTP runtime, and finally the P150 part:

- **The P150 expert set** (35 GB: the BFP4 expert rows, the precision plan and the MTP drafter's experts) is downloaded
  from [Lottolabs/Qwen3.8-Flash-Next-Coder-P150](https://huggingface.co/Lottolabs/Qwen3.8-Flash-Next-Coder-P150) at
  the revision pinned in `tt/artifacts.json`, resumable and SHA-256-checked, into `FNX_DATA` (default
  `<Strata data folder>/tt`). `HF_ENDPOINT` selects a mirror.
- Instead of downloading, it can be rebuilt from the GGUF on an NVIDIA GPU (16 GB or more, about 55 GB of RAM, about an
  hour on an RTX 3090): `python3 tt/tools/tt_artifacts.py regenerate --data DIR --gguf SHARD1 --mtp RT`. The drafter's
  routing profile (`mtp/expert-profile.npy`) is a measurement on the card and is fetched either way
  (`tt_artifacts.py fetch --data DIR --only mtp/expert-profile.npy`). The calibration sequences of the published set
  are not published (they include local source trees of the machine that made them), so elsewhere `regenerate` needs
  your own `--calib seqs.json` and its GPTQ rows will differ from the published ones; check the result with the
  quality gate (`tt/fnx/eval`). On the machine that made the set, layer 0's rows, the plan and the MTP experts came out
  bitwise equal to the published files.
- The CPU expert library the engine needs (`tt/cpu_experts`, Strata's own CPU kernels) is built inside the image.

Start it later with `./setup.sh --backend tt` (or the `run-coder-iq1_m.sh` it writes). The first start builds the
caches (dequantized weights, converted tensors, compiled kernels), which takes a while; later starts load in about a
minute and a half.

**A card shared with other jobs.** The engine takes a lock file before it touches the card
(`/var/tmp/gemma4-12b/device.lock` by default, `FNX_DEVICE_LOCK` to change it) and waits while another job holds it.
The model unloads after 15 idle minutes (`idle_unload_s` in the config) to give the card back; the next request loads
it again. The server's own start timeout is off for this engine (the lock wait has no upper bound); the engine instead
ends itself if it is not ready `FNX_READY_S` seconds (900) after it got the lock, and a hung engine is removed and the
board reset before the lock is released.

**The Monitor** shows the card's temperature, power, clock and PCIe link (from the driver's sysfs); the card reports
no load or memory use.

## Limits

- Coder IQ1_M through setup; IQ3_S from a development checkout only (above). Other models would need their own
  expert set and a quality check.
- Context up to 32,768 tokens; one request at a time (no `parallel`); no images.
- Linux only, one card.
- Start through `./setup.sh --backend tt` or the run script. A plain `./setup.sh` does not know the P150 install and
  may try to set up a CUDA engine on a PC that also has an NVIDIA card.

## Checking an install

`tt/tools/validate_all.sh` runs every test of the engine (module tests against numpy references, traced vs eager
bitwise, speculative == plain, the serving protocol and HTTP). `python3 tools/test_setup_tt.py` tests the setup path
without the card.
